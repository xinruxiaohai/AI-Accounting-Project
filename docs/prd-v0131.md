## 一、产品目标

用一句话：**把分类彻底隔离到用户维度，并把「默认分类 / 图标 / 主题」三套素材从「够用」扩到「开箱好用」，再补上 3-5 个不引发大规模重构的高频实用功能。**

不在本次范围（已完成或已列入 v0.14）：预算、soft delete 回收站、CSV/Excel 导入导出、支付宝/微信账单解析、AI 自然语言记账与 Few-Shot 记忆库、报销、借贷、联系人、相册、通知中心、多用户 JWT、后台管理、SQLite 备份恢复。

**A1 迁移位置说明（工程师核对后修订）**
- `init_db()` 是一个整体函数（795~1157 行）：categories 的 DDL 在 917-925 行，旧唯一索引在 944-946 行；`_ensure_user_schema()` 的**函数定义在 614 行、调用点在 1130 行**（即所有 DDL 跑完之后）。
- 结论不变：给 categories 补 user_id 的 ALTER 必须排在 categories 表建好之后。两种放法都安全：① 放在 928~946 那段 `type`/`sort_order` 的列检查里；② 放在 `_ensure_user_schema()` 里（它本来就专职补列，1130 行才执行）。**任选其一，不要两处都放。**
- 无论放哪，`ALTER` 都要写成带 `NOT NULL DEFAULT 1` 的显式默认值，历史数据天然归 1 号管理员，与「老数据归 1 号」的迁移策略一致。

### C 部分补充（工程师核对后新增）

**1）「同步最新默认分类」按钮的落点（A7）—— team-lead 已裁定**
- **归属：分类管理弹窗（`#category-modal`），不放系统设置。** 理由：用户心智是「我在管分类，发现没有想要的，所以同步」；放系统设置他会找不到。基线提交落地后 `#new-category-type` 变成已提交历史、冲突源消失，不应为规避一个即将不存在的冲突牺牲语义正确性。
- **具体位置（插入点已实测确认）**：`.category-add-wrap`（index.html 1591-1604）结束之后、`<p class="drag-hint">`（1606）之前 —— 即输入行下方、分类树上方，**不碰那四个控件，也不依赖 1595~1598 那个节点的坐标**。
- **样式**：沿用项目现成的 `btn btn-light btn-sm`（与通讯录 / 相册 / 回收站三张卡的按钮同款），不与 `添加` 抢视觉重心。
- **文案**：`没有想要的分类？` + 次要按钮「同步最新默认分类」（**不要用 primary**，`添加` 才是该行主操作）。
- **行为口径**：幂等、只补不覆盖；用户删过或改名过的分类不会被灌回来。成功 Toast「已补充 N 个分类」。

**2）停用项（C2b / C2c）的口径已钉死**
- 编辑态保分类：采用「把当前记录自带的分类**合成临时 `<option>` 注入 select option 列表** + 网格同步渲染该格」的双层方案（C2b-1 数据层 + C2b-2 视觉层），**不采用** `include_archived=1` 查询参数（避免多一次请求、也避免列表语义被稀释）。
- **只补网格不补 option 是无效的**：真正决定保存值的是隐藏 select（`#category` / `#sub-category`），不是网格；select 无匹配项时会回落到「列表第一项」而非空。
- 历史账单显示零影响：不需要额外处理。
- 停用项过滤必须覆盖 5 处渲染点 + 1 个排序接口，见 C2c。
- 术语更正：`collectCategoryValues()`（4231）是**分类管理弹窗里新建分类**的表单取值函数（读 `new-category-name` / `new-category-parent` / `new-category-type`），**不是记账表单取值函数**；记账表单的取值函数是 `selectedCategoryId()`（820），不要找错。

**3）A6 调用失败的容错口径已钉死（A6b）**
- 注册流程 / 登录静默兜底：静默失败，仅 console 留痕，不弹 Toast。
- 设置或分类管理里的按钮：Toast 明确报错。
