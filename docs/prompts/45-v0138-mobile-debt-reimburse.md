# 45 · v0.13.8-DEV 终极补丁：移动端真机适配 + 借贷/报销业务闭环

## 需求背景

v0.13.7 的移动端响应式只在桌面模拟器里验证过，用户拿到真机后发现三类问题：① 底部 Tab Bar 被 iPhone 小白条压住；② 聚焦输入框时 iOS Safari 自动放大页面（字号 < 16px 触发）；③ 旧 Service Worker 缓存顽固，手机上刷新多次仍吃旧样式。同时，资产页的「借入 / 借出 / 待报销」点开后只是一行行文字，看不出还剩多少没还，也没有任何操作入口——还款、报销都得绕到别的页面手工记一笔，业务上是断的。

## 核心 Prompt（摘要）

1. 击穿缓存：`service-worker.js` 的 `CACHE_NAME` 升 `ai-accounting-v0.13.8-r1`，静态资源版本号全部 bump 到 `?v=0.13.8`。
2. 真机兼容：≤768px 侧边栏绝对隐藏、强制显示底栏；底栏加 `padding-bottom: env(safe-area-inset-bottom)`；所有 input/textarea `font-size:16px`；viewport 加 `viewport-fit=cover`。
3. 借贷/报销明细改成卡片列表：联系人、日期、本金、剩余待还、状态（未结清/已结清/已逾期）；每卡有【还款/结清】【编辑】【删除】。
4. 还款：弹窗选还款账户 + 填金额 → 后端扣账户余额、生成一条 expense/income 流水且备注关联债务 ID、债务置为已结清并置灰。
5. 报销：同理加【标记为已报销】，生成收入流水并更新状态；无记录显示友好空状态。

## 方案简述

- **安全区只加在底栏与内容区**：`env(safe-area-inset-bottom)` 在非刘海机上解析为 0，不会引入多余留白；同时在 `.content` 底部预留 `--mtab-h + 20px + safe-area`，避免最后一张卡片被底栏遮住。
- **16px 必须 `!important`**：`.form-control` 自身声明了 14px 且同权重，移动端块靠文件末尾顺序只能覆盖未声明场景，所以直接提权。
- **`repaid` 而不是改 `status` 语义**：部分还款必须能表达「还了 40 还剩 60」，因此单独存已还本金，`remaining` 统一由数据层算，前端只读，避免多处口径漂移。
- **还款/报销都走「生成真实流水」而不是只改状态**：钱真的动了（账户余额变化），账本里必须有一条可追溯的账目，否则统计与明细会对不上；备注里写 `#债务ID` / `#账目ID` 是为了人工排障时能反查。
- **单事务**：`repay_debt` / `reimburse_record` 在一个连接里完成「插流水 + 改余额 + 改债务」，任何一步失败整体回滚。
- **卡片重绘而非局部更新**：操作成功后 `refresh()` 拉全量再 `reopenStatDetail()` 重画，避免局部状态与后端不一致（代价是弹窗会闪一下，用 `reopenStatDetail()` 只在弹窗仍打开时重绘来收敛）。

## 踩坑结论

1. **`findRecordById()` 的严格比较**：`item.id === recordId`，但 `data-id` 属性取出来是字符串，导致「标记为已报销」静默无反应（`openReimburseModal` 收到 `null` 直接 return，连报错都没有）。改为 `String()` 比对。
2. **重复打开同一个 Bootstrap Modal**：实例复用不会重置输入值，必须在 `openXxxModal()` 里重新写金额/日期/账户，否则第二次会沿用上次的数值。
3. **测试点击旧节点**：明细重绘后原按钮已脱离文档，`b.click()` 无副作用，必须每次重新查询。
4. **`getComputedStyle().height` 恒为像素**、安全区在模拟器里恒为 0——这类断言只能查 CSS 文本与计算后的 padding 下限。
5. 改完模板必须重启 `--no-reload` 的 Flask，否则 CDP 拿到旧 DOM（老坑）。
6. 自动化跑之前要重置测试数据（`make_v138_user.py cleanup/create`），否则重复运行会把债务还到只剩零头，卡片金额断言全错。
