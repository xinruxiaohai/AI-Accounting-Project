## 四、硬约束（违反即失败）

1. **严禁调用 `/register`**。只能用 `test@test.com` 登录换 JWT。
2. **先备份再写**：`cp /opt/zhihuizhang/records.db /opt/backups/records_pre_seed_v2_$(date +%Y%m%d-%H%M%S).db`，记录备份前后 md5 与文件大小。
3. **写入必须走 API，不许直接 `INSERT`**。账户余额由后端维护，直改 SQL 会破坏平账。
4. **`POST /api/records` 必须传 `category_id`（数字）**。传 `category` 文本会触发 `ensure_category` 自动建分类，污染分类表——这是上一轮踩过的坑。
5. **`PUT /api/records/<id>` 是整条覆盖**，字段缺一个就 400。本轮原则上不要 PUT 已有记录。
6. **不许改动已有 283 条**，只做新增。
7. **幂等**：重跑必须新增 0 条。用固定前缀 `[DEMO-V2-20261118]` + 业务键（日期+分类+金额+备注）的 sha256 去重，写之前先查库里是否已存在。
8. **`DELETE /api/records/<id>` 走 `soft_delete_record` 会自动回滚余额**，teardown 里不要再调 `adjust_balance`，否则二次入账。
9. 测试/调试产生的临时账单必须在 teardown 阶段清干净，并复算平账。

## 六、执行步骤（严格按序，不要跳）

1. **只读盘点**：查 uid3 现有账户清单、各账户当前余额、已有分类 id（一级+二级完整映射）、已有 283 条的日期分布。
2. **备份**：`cp records.db /opt/backups/records_pre_seed_v2_<时间戳>.db`，记录 md5。
3. **生成计划**：把这 40–60 条写成清单（日期 / 类型 / 一级 / 二级 / 金额 / 账户 / 备注），先 `--plan` 空转打印，**不要写库**。
4. **自检计划**：总量在 40–60 之间、6 个必覆盖分类都有、金额区间合理、日期不超出区间、账户都存在。
5. **执行写入**：逐条 `POST /api/records`（带 `category_id`），每条后检查 HTTP 状态。
6. **平账复算**：拉所有账户，按 `期初 + 收入 − 支出 − 转账 = 当前余额` 独立复算，**差额必须全部 0.00**。
7. **幂等验证**：把同一份计划再跑一次，断言新增 0 条。
8. **截图验收**：走隧道用 headless Edge 截图——首页分类占比环形图（应出现宠物/汽车等）、图表页分类统计。
9. **清理**：结束所有临时进程，确认没有残留测试数据。
